# 自律開発サイクルの詳細(調査→設計→実装→テスト)

このドキュメントは `CLAUDE.md` の「ワークフロー全体像」「厳守ルール(ゲート)」で定義される4フェーズサイクルの詳細な仕組みを定義する。`CLAUDE.md` から参照される。フェーズの存在自体・ゲートの数(2箇所)・実装フェーズでメインエージェントがコードを書かない、という原則は `CLAUDE.md` 側の「厳守ルール(ゲート)」が最終的な正であり、本ドキュメントはその実現方法(仕組み)を記述する。

## 設計・実装のレビューループ(自動、最大2ラウンド)

`/design` の設計ドキュメント作成後(人間確認ゲート1の前)と、`/implement` の実装完了後(`/test` の前)には、それぞれ作成者とは別のサブエージェントによるレビューを挟む。**このレビューは人間を介さない自律的なチェックであり、新たな人間確認ゲートを追加するものではない。** 人間確認ゲートは引き続き2箇所(設計後・テスト後)のみ。

### 仕組み

1. 設計後: `design-reviewer` が設計ドキュメント(と対応する調査ドキュメント)をレビューし、`PASS` か `MAJOR` を判定する。
2. 実装後: `code-reviewer` が設計ドキュメントとワークツリー内の実装差分をレビューし、同様に判定する。
3. `MAJOR` の場合、作成者(designer/implementer、または呼び出し元)が指摘に基づいて修正し、同じレビューアーに再レビューを依頼する(ラウンド2)。
4. ラウンド2の結果に関わらず、それ以上は自動でループしない(最大2ラウンド)。ラウンド2で `MAJOR` が残った場合は、その指摘を隠さず**直後の人間確認ゲートの提示内容に明記**し、最終判断を人間に委ねる。
5. 各ラウンドの判定・主な指摘は、設計ドキュメントの「設計レビュー結果」「コードレビュー結果」欄、テストレポートの「コードレビューからの引き継ぎ」欄に記録する。

### レビューアーの独立性

`design-reviewer`・`code-reviewer` は自分では設計・実装を行わない、レビュー専任のサブエージェントである。指摘のみを行い、修正は元の担当(designer/implementer)に委ねる。「書いた本人が自分のミスに気づけない」状態を避けるのが目的なので、レビューを著者自身に兼任させない。

さらに、`design-reviewer`・`code-reviewer` は著者(`designer`/`implementer`)とは**異なるモデル**(`opus`)を使う。同じモデルで書いてレビューすると、そのモデル特有の盲点(見落としがちな観点、思い込みの癖)がレビューでもすり抜けやすい。別モデルに読ませることで、その盲点を補完する。

## 調査フェーズの並列化(ファンアウト)

1つのトピックの中に、互いの結果を待たずに独立して調べられる観点が複数ある場合(例:「ライブラリ選定」「既存アーキテクチャとの整合性」「パフォーマンス制約」)、`/investigate` は `investigator` サブエージェントを**同一メッセージ内で複数回呼び出す並列dispatch**によって観点ごとに分担調査させてよい。詳細な手順は `.claude/commands/investigate.md` に定義されている。要点は以下。

- 分解は観点が真に独立している場合のみ行う。観点同士が依存する場合や観点が1つしかない場合は分解しない。分解しても2〜4観点程度に留める。
- 各投入先には出力パス(`docs/investigations/_parts/<topic-slug>/<sub-slug>.md`)を明示し、investigator自身にパスを決めさせない。
- **並列実行中のサブエージェントは `docs/memory/` に直接書き込まない。** 複数エージェントが同時に `MEMORY.md` を編集すると内容が競合・上書きされるため、各エージェントは再利用可能な知見を「メモリ候補」として最終報告に含めるに留め、実際の書き込み(重複排除を含む)は全員の完了後にorchestrator(呼び出し元のメインの会話)が1回でまとめて行う。
- 全観点の結果が揃ったら、矛盾がないか確認したうえで単一の `docs/investigations/YYYY-MM-DD-<topic-slug>.md` に統合する。観点間で結論が食い違う場合は黙って一方を採用せず「未解決の疑問」として残す。
- この並列化パターンは調査フェーズ専用に定義しているが、設計・実装・テストの各フェーズで同様に独立したサブタスクへの分解が可能だと判断した場合、同じ原則(出力パスの明示、共有メモリへの書き込みはorchestratorに集約)を踏襲して拡張してよい。

## ワークツリー分離(複数セッション対応)

このプロジェクトは、複数のセッション(異なるターミナル/チャットから起動された複数のClaude Codeインスタンス)が同時に同じリポジトリを修正することを想定している。共有の作業ディレクトリを複数セッションが同時に書き換えると、チェックアウト中ブランチの奪い合い・コミットの混線・`docs/memory/MEMORY.md` 等の共有ファイルの競合が起きるため、**`/investigate` の開始時点でトピック専用の git worktree を作成し、`/design` → `/implement` → `/test` まで同じワークツリーを使い続ける。**

### 仕組み

1. `/investigate` は調査を始める前に、ベースブランチ(既定は `main`。ユーザーが明示的に別ブランチを指定していればそちら)から `git worktree add -b <topic-slug> .claude/worktrees/<topic-slug> <base-branch>` でトピック専用のワークツリー・専用ブランチを直接作成し、`EnterWorktree(path: ...)` でそこに入る。**ベースブランチ側の共有ディレクトリの状態(チェックアウト中のブランチ)は変更しない。** これは意図的な選択で、以前は共有ディレクトリで目的のブランチへ`checkout`してから`EnterWorktree(name: ...)`(`worktree.baseRef: "head"`、現在の実行ディレクトリのHEADから分岐)を使っていたが、複数セッションが同時に別々のベースブランチを指定すると`checkout`同士が競合し、意図しないブランチから分岐しうるレースコンディションがあったため、共有ディレクトリに触れない`git worktree add`方式に切り替えた。トピック用ワークツリーが既に存在する場合(他セッションまたは自分自身が既に開始済み)は新規作成せず、`EnterWorktree(path: ...)`で入るだけでよい。
2. `/design`・`/implement`・`/test` はこのワークツリー内で継続する(再度 `EnterWorktree` で新規作成はしない。セッションが既に入っていなければ `path:` で既存ワークツリーに入り直す。別トピックのワークツリーに入ったままの場合は先に `ExitWorktree(action: "keep")` で抜けてから入り直す)。実装フェーズでは複数の `implementer` が並列で動くことがあるため、コミットは原則としてメインエージェントがタスク単位でまとめて行う(詳細は「実装フェーズのタスク分割・並列化」節)。ベースブランチとは分離されているため、こまめなコミット自体は安全。
3. `/test` のゲート2で人間が「承認してクローズ」を選んだ場合にのみ、`ExitWorktree(action: "keep")` でベースブランチに戻り、`git merge <topic-branch>` でベースブランチへ統合する。マージがコンフリクトした場合は自動解決せず人間に報告する。**マージがクリーンに完了したら、続けて必ず `git push origin <base-branch>` を実行してから**ワークツリーとブランチを削除する(pushはマージ手順の一部であり、別途人間の指示を待たない。詳細は `CLAUDE.md` 厳守ルール8)。**この直接merge+push方式は、`docs/process/git-workflow.md` が定義する目標状態(PRベース、main/developへの直接push禁止)への移行が完了するまでの暫定運用である。両ドキュメントの「現状の差分・移行TODO」を参照。**
4. ゲート2で「修正依頼」「設計からやり直し」が選ばれた場合は、ワークツリーを削除せずそのまま残し、同じブランチ内で作業を継続する。

### 複数セッションでの並行作業

セッションAがtopic Xを、セッションBがtopic Yを同時に `/cycle`(または個別コマンド)で進めている場合、それぞれ別のワークツリー(`.claude/worktrees/topic-x`、`.claude/worktrees/topic-y`)・別のブランチで作業するため、調査・設計・実装・テストの全フェーズでファイル競合は起きない。ただし以下は既知の制限であり、このリポジトリでは未対応:

- あるトピックのワークツリーは、作成された時点のベースブランチの状態(特に `docs/memory/`)を引き継ぐ。作成後にベースブランチへマージされた他トピックの決定・規約は、このワークツリーには自動反映されない(通常の git worktree の性質上の制限)。長時間かかるトピックでは、`/design` 等の途中でベースブランチの最新を取り込むべきか判断してよい。
- 複数トピックのブランチが同時にベースブランチへマージされる場合、`docs/memory/MEMORY.md` など共有ファイルでマージコンフリクトが起きる可能性がある。この場合もゲート2の手順どおり自動解決せず人間に報告する。

## 実装フェーズのタスク分割・並列化

`/implement` を実行するメインエージェント(オーケストレーター)は、**自分でコードを実装しない。** 設計ドキュメントの実装ステップを `TaskCreate` でタスクに分割し、依存関係のないタスクは `implementer` サブエージェントへ並列dispatchし、`TaskList`/`TaskUpdate` で進捗を確認・記録する役割に徹する。詳細な手順は `.claude/commands/implement.md` に定義されている。要点は以下。

- タスク分割は必須。実装ステップが1つしかない場合でも、必ず `TaskCreate` でタスク化してから `implementer` に委譲する。メインエージェントが直接ファイルを編集することはない。
- **タスクはトピックをまたいで1つの共有リストに並ぶ。** 複数セッションが別トピックを同時に実装しうるため、各タスクの `subject` には必ず `[<topic-slug>]` プレフィックスを付け(`metadata.topic` にも設定)、`TaskList` を見る際は自トピックのプレフィックスで絞り込む。他トピックのタスクには触れない。
- タスク間の依存関係は `TaskUpdate` の `addBlockedBy`/`addBlocks` で明示する。**同じファイルを変更する複数のタスクは並列化せず、順序づける。** 依存がなく変更対象ファイルも重ならないタスクだけを並列化の対象にする。
- 依存の解決済みタスク群(ウェーブ)は、`implementer` を**同一メッセージ内で複数回呼び出して並列実行**する。各`implementer`は着手時に `TaskUpdate` で `owner`・`status: in_progress` を設定し、完了時に `status: completed` にする(未完了・エラー残りは `completed` にしない)。
- **並列dispatch中の `implementer` は `git commit` を自分では行わない。** 同一ワークツリー内での競合を避けるため、ファイル変更のみ行い、メインエージェントがタスク完了報告を受けるたびにコミットする。コミットは実装ではなく記録作業なので、これはメインエージェント自身が行ってよい。
- 並列dispatch中は `implementer` も共有メモリへ直接書き込まない(ファンアウトと同じ理由・同じ原則)。メモリ候補として報告し、メインエージェントがウェーブ完了ごとに集約して反映する。
- コードレビュー(`code-reviewer`)は全タスク完了・コミット後に1回行う。`MAJOR`判定の修正も新しいタスクとして`TaskCreate`し`implementer`に委譲する(メインエージェントが直接修正しない)。

## 成果物の命名規則

`YYYY-MM-DD-<topic-slug>.md` で統一する。同一トピックの調査・設計・テストは同じslugを使い、相互にリンクを張ること(例: 設計書の冒頭に対応する調査ドキュメントへのリンクを置く)。`docs/process/git-workflow.md` が定義するブランチ名(`feature/<topic-slug>`・`hotfix/<incident-slug>`)もこのslugと対応させる。

## サブエージェントの使い分け

- **investigator**: 読み取り専用に近い調査(Web検索・コード探索)。実装はしない。
- **designer**: 調査結果を踏まえて設計書を書く。コードは書かない。
- **design-reviewer**: designerとは別の視点で設計書をレビューする。自分では書き直さない。
- **implementer**: `TaskList`で割り当てられた単一タスクの範囲だけを実装する。設計にない範囲を勝手に広げない。並列dispatch中は自分でコミットも共有メモリへの書き込みも行わない。
- **code-reviewer**: implementerとは別の視点で実装をレビューする。自分では修正しない。
- **tester**: 実装を検証し、レポートを書く。テストを通すためにテスト自体を歪めない(テストコードの改変は原則implementerの担当に戻す)。

各フェーズはメインの会話コンテキストを汚さないよう、可能な限り対応するサブエージェント(Agent tool)に委譲する。**特に実装フェーズは、メインエージェントが自分で実装することを禁止し、`TaskCreate`/`TaskUpdate`/`TaskList`によるタスク分割・並列dispatch・進捗確認を必須とする。**
