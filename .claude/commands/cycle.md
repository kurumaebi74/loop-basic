あなたはこれから「調査・設計・製造・テスト」の1サイクルを、対象トピックについて最初から最後まで実行する。

トピック: $ARGUMENTS

## 実行順序

1. `/investigate $ARGUMENTS` の内容に沿って調査を行い、`docs/investigations/` に記録する。この段階ではまだベースブランチ(通常の作業ディレクトリ)で作業する。
2. `/design $ARGUMENTS` の内容に沿って設計を行い、`docs/designs/` に記録する。これもベースブランチで作業する。
3. **人間確認ゲート1**: `AskUserQuestion` で設計の承認を得る(承認/修正依頼/差し戻し)。承認が得られるまで手順4に進んではならない。修正依頼・差し戻しの場合は該当フェーズに戻ってやり直し、再度このゲートに戻る。
4. `/implement $ARGUMENTS` の内容に沿って実装する。**このコマンドは実装開始前に、このトピック専用の git worktree を作成・使用する**(詳細は `.claude/commands/implement.md`)。複数セッションが同時に別トピックを実装しても、それぞれ別のワークツリーで作業するため衝突しない。
5. `/test $ARGUMENTS` の内容に沿って、`/implement` で作成したワークツリー内でテストし、`docs/tests/` に記録する。
6. **人間確認ゲート2**: `AskUserQuestion` でテスト結果の承認を得る(承認してクローズ/修正依頼/設計からやり直し)。承認が得られるまでこのサイクルを完了扱いにしてはならない。修正依頼・差し戻しの場合は該当フェーズ(手順4または2)に戻り、ワークツリーはそのまま維持して作業を続け、再度ゲート2に戻る。
7. 承認が得られたら、`/test` の「ゲート通過後のワークツリー処理」に従ってトピックのブランチをベースブランチにマージし、ワークツリーを削除する。マージがコンフリクトした場合は自動解決せず人間に報告する。
8. マージ完了後、サイクル完了を宣言し、成果物(調査・設計・テストの各ドキュメントへのパス)を要約して報告する。

## 運用上の注意

- 各フェーズは可能な限り対応するサブエージェント(`.claude/agents/investigator.md` 等)に委譲し、メインの会話コンテキストを圧迫しないようにする。ただし委譲する場合も、ゲートでの人間確認は必ずメインの会話(このコマンドを実行しているセッション)で行うこと。委譲先のサブエージェントに承認判断をさせてはならない。
- `EnterWorktree`/`ExitWorktree` はこのメインセッション自身の作業ディレクトリを切り替えるツールである。`/implement`・`/test` で `implementer`・`tester` サブエージェントに委譲する場合、委譲はメインセッションがワークツリーに入った**後**に行い、サブエージェントがそのワークツリー配下で作業するようにすること。
- 各フェーズ(サブエージェントに委譲する場合はその内部)は `docs/memory/MEMORY.md` を介して知識を共有する。あるフェーズで得られた再利用可能な知見(decision/convention/pitfall/glossary/open-question)は、そのフェーズの完了時点で `docs/memory/entries/` に反映されている前提で次フェーズに進んでよい。サイクル全体が終わったら、`docs/memory/MEMORY.md` に新規・更新エントリがあれば要約に含めて人間に報告する。
- 手順の途中で致命的な不確実性(要件不明、認証情報が必要、破壊的操作が必要 等)にぶつかった場合は、定義されたゲート以外の場所でも停止して人間に確認してよい。
- 何度もゲートで差し戻しが続く場合(目安: 同一ゲートで3回以上)は、一旦サイクルを中断し、根本原因(要件定義そのものが曖昧である等)を人間と一緒に整理することを提案する。
