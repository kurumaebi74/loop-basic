あなたはこれから「製造(実装)」フェーズを実行する。対象トピック: $ARGUMENTS

**このコマンドを実行しているあなた自身(メインエージェント)は、コードを1行たりとも自分で実装してはならない。** あなたの役割は (1) 設計をタスクに分割する、(2) 依存関係のないタスクを `implementer` サブエージェントへ並列dispatchする、(3) `TaskList`/`TaskGet` で進捗を確認する、(4) 完了報告を受けてコミット・取りまとめを行う、の4つに限られる。ファイルの編集・作成は必ず `implementer` を通じて行うこと。たとえ実装ステップが1つしかない場合でも、必ずタスク化して `implementer` に委譲し、自分で編集しない。

## 前提条件の確認

1. `docs/designs/` から対象トピックに対応する設計ドキュメントを読む。存在しない場合は `/design` の実行を提案して停止する。
2. **この設計が人間に承認済みであることを確認する。** 会話履歴やユーザーの直近の指示から承認が確認できない場合は、実装を始める前に「この設計は承認済みか」を人間に確認すること。無承認のまま実装を進めてはならない。

## ワークツリーの確認(必須・コード変更前に必ず行う)

このフェーズは `/investigate` が作成したトピック専用ワークツリー内で実施する(調査・設計ドキュメントがそこにあるため)。**ファイルを1つでも変更する前に、必ずこのワークツリーに入っていることを確認する。**

1. 現在のセッションが既にこのトピック用のワークツリーに入っているか確認する(`/cycle`から連続で呼ばれる場合、または同一セッションで`/investigate`・`/design`から続けて呼ばれる場合)。入っていれば手順2は不要。
2. 入っていない場合、`EnterWorktree` を `path: .claude/worktrees/<topic-slug>` で呼び出して該当ワークツリーに入る。ワークツリーが存在しない場合は `/investigate` がまだ実行されていない可能性が高いので、その旨を報告して停止する。

以降のタスク分割・`implementer` サブエージェントへの作業指示・コミットは、すべてこのワークツリー内で行う。他のセッションが並行して別トピックの `/implement` を実行していても、それぞれ別のワークツリー(別ディレクトリ・別ブランチ)で作業するため、ファイルの奪い合いは起きない。

## タスク分割・並列実装(必須)

実装に着手する前に、必ず設計ドキュメントの実装ステップをタスク化する。依存関係のないタスクは並列でimplementerに実装させ、依存があるタスクは順序を守って実行する。

1. 設計ドキュメントの実装ステップ(チェックリスト)を読み、実装単位に分解する。1ステップが大きすぎる場合はさらに細かく分ける。**設計ドキュメントの「テスト戦略」に自動テストの新規作成が明記されている場合、それも独立したタスクとしてここに含める**(実装コードと同時に、あるいは実装タスクの後続タスクとして)。各タスクの説明には、そのタスクだけを渡された `implementer`(この会話の文脈を持たない)が着手できるだけの情報を含める(対象ファイル、やること、参照すべき設計ドキュメントの節・パス)。
2. `TaskCreate` で各タスクを作成する。**このプロジェクトは複数トピックが同時並行で動きうるため、タスクは必ずトピックを識別できる形にする。** `subject` の先頭に `[<topic-slug>]` を付与し(例: `[add-login] スキーマ変更`)、`metadata` に `{"topic": "<topic-slug>"}` を設定する。既存タスクと重複しないか事前に `TaskList` で確認する。
3. タスク間の依存関係を洗い出し、`TaskUpdate` の `addBlockedBy` / `addBlocks` で明示する。**同じファイルを変更する複数のタスクは並列化の対象にせず、依存関係として順序づける。** 依存がなく、かつ変更対象ファイルが重ならないタスクだけが並列化の候補になる。
4. `TaskList` を呼び、**`subject` の `[<topic-slug>]` プレフィックスで自トピックのタスクだけに絞り込んだうえで**、「pending・未所有・blockedByが空」のタスクをまとめて1つの「ウェーブ」とする。他トピックのタスク(別のプレフィックスが付いているもの)は無視すること。そのウェーブ内のタスクを**同一メッセージ内で `implementer` サブエージェントを複数回呼び出して並列実行する**(Agent toolを1レスポンス内で複数回呼ぶ)。各呼び出しには対象の `taskId` とタスク内容、設計ドキュメントへのパスを明示する。
5. 各 `implementer` は着手前に `TaskUpdate` で自タスクの `owner` を自分自身に設定し `status: in_progress` にする。完了したら `status: completed` にする。**テストが失敗する・実装が部分的・未解決のエラーが残る場合は `completed` にせず `in_progress` のまま理由を添えて報告する。**
6. **並列dispatch中の `implementer` は `git commit` を自分では行わない。** 同一ワークツリー内で複数プロセスが同時にコミットすると競合するため、ファイルの編集のみ行い、変更内容を呼び出し元に報告する。メインエージェントは、各タスクの完了報告を受けるたびにそのタスク分をコミットする(`git add` + `git commit`、意味のある単位で1タスク1コミットが目安)。**これは実装ではなく記録作業なので、メインエージェント自身が行ってよい。**
7. 1ウェーブが完了したら `TaskList` で(自トピックのタスクに絞って)状態を確認し、次に着手可能になった(blockedByが解消された)タスクで次のウェーブを組み、手順4〜6を繰り返す。自トピックの全タスクが `completed` になるまで続ける。
8. 実装中に他topicでも再発しうる落とし穴(pitfall)を `implementer` が見つけた場合、**並列dispatch中は共有メモリへ直接書き込まず、完了報告に「メモリ候補」として含める。** メインエージェントがウェーブ完了ごとに集約し、重複・矛盾を解消してから `docs/memory/entries/` へ反映する(調査フェーズのファンアウトと同じ原則。詳細は `.claude/commands/investigate.md` 参照)。
9. 依存関係が強く並列化の余地がない場合(タスクが1つ、または全タスクが直列にしか実行できない)でも、`implementer` への委譲そのものは省略しない。

## 各タスクの実装方針(`implementer` が従う内容)

`implementer` に渡す各タスクは、以下の方針で実装する(詳細は `.claude/agents/implementer.md` にも定義)。

1. 着手前に `docs/memory/MEMORY.md` を読む。特に convention(実装規約)・pitfall(既知の落とし穴)は関連するものを `docs/memory/entries/` で確認し、それに従う。
2. 割り当てられたタスクの範囲を超えて実装を広げない(スコープクリープの禁止)。設計との乖離が必要だと判明した場合は、作業を止めて理由をメインエージェントに報告する(メインエージェントが人間に報告し、設計ドキュメントを更新してから続行する)。既存の共有メモリ(decision/convention)と矛盾する実装が必要な場合も同様。
3. 意味のある単位でこまめに動作確認しながら進める。
4. 完了したら、設計ドキュメントの実装ステップのチェックリストのうち該当箇所にチェックを入れる。

## コードレビュー(必須・自動、最大2ラウンド)

全タスクが `completed` になり、メインエージェントが最後のコミットを終えたら、`/test` に進む前に実装を検証する。**このレビューを省略して `/test` に進んではならない。**

1. `code-reviewer` サブエージェントに、設計ドキュメントのパスと、このワークツリー内の実装差分(ベースブランチとの `git diff` で確認できる範囲)を渡してレビューを依頼する(ラウンド1)。
2. 判定が `PASS` の場合、指摘(あれば軽微なもの)を記録し `/test` に進む。
3. 判定が `MAJOR` の場合、指摘内容を修正タスクとして `TaskCreate` し(`subject` に `[<topic-slug>]` プレフィックス、`metadata.topic` も同様に設定する)、`implementer` に委譲して修正する(メインエージェント自身は修正しない)。修正が完了したら `code-reviewer` に再レビューを依頼する(ラウンド2)。
4. ラウンド2の判定に関わらず、それ以上は自動でループしない。ラウンド2で `MAJOR` が残った場合は、その指摘を**テストレポートおよびゲート2の提示内容に引き継ぐ**(`/test` 側で扱う)。
5. 実施したラウンド数・各ラウンドの判定を設計ドキュメントの実装ステップ欄など分かる場所に簡潔に記録する。

## 完了条件

- `TaskList` を自トピックの `[<topic-slug>]` プレフィックスで絞り込んで確認し、実装タスクがすべて `completed`(または明確に不要と判断され `deleted`)になっている
- コードレビューが完了している(PASS、またはラウンド2終了後の状態。未解決のMAJORがあれば引き継ぐ内容が明確になっている)
- 実装内容がこのトピックのワークツリー内でコミットされている(メインエージェントによるタスク単位のコミット)
- 次のアクションとして `/test` の実行を促すメッセージを出す

## 注意

- このフェーズには人間確認ゲートはない。実装完了後は自動的に `/test` に進んでよい(同じワークツリー内で継続する)。ただし、設計からの逸脱・重大な技術的制約に直面した場合はその場で人間に報告してよい。
- ベースブランチへの `git merge` や `git push` は誰も(メインエージェントも `implementer` も)自分で行わない。マージは `/test` でのゲート2承認後にのみ行う。
- 繰り返しになるが、**メインエージェントは実装しない。** タスクが1つでも、緊急でも、この原則を崩さない。
