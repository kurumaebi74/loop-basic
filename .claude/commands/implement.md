あなたはこれから「製造(実装)」フェーズを実行する。対象トピック: $ARGUMENTS

## 前提条件の確認

1. `docs/designs/` から対象トピックに対応する設計ドキュメントを読む。存在しない場合は `/design` の実行を提案して停止する。
2. **この設計が人間に承認済みであることを確認する。** 会話履歴やユーザーの直近の指示から承認が確認できない場合は、実装を始める前に「この設計は承認済みか」を人間に確認すること。無承認のまま実装を進めてはならない。

## ワークツリーの分離(必須・コード変更前に必ず行う)

このプロジェクトは複数セッションが同時に同じリポジトリを修正することを想定している。共有の作業ディレクトリで複数セッションが同時に書き換えると、チェックアウト中ブランチの奪い合いやコミットの混線が起きるため、**ファイルを1つでも変更する前に、必ずこのトピック専用の git worktree に入る。**

1. ワークツリーを作る前に、現在のディレクトリ(ベースブランチ)に未コミットの変更(直前の `/investigate` `/design` で作成された調査・設計ドキュメント、共有メモリの更新など)がないか確認する。あれば `git add` してコミットする(例: `docs(<topic-slug>): investigation and design`)。これを怠ると、これから分岐するワークツリーにその変更が含まれない。
2. 現在のセッションが既にこのトピック用のワークツリーに入っているか確認する(`git branch --show-current` が topic由来のブランチ名になっているか等)。既に入っていれば手順3・4は不要。
3. まだ入っていなければ `EnterWorktree` ツールを `name: <topic-slug>` で呼び出す。セッションの作業ディレクトリが `.claude/worktrees/<topic-slug>` 上の新しいブランチへ切り替わる(分岐元はこのプロジェクトの `.claude/settings.json` の `worktree.baseRef: "head"` によりローカルHEAD)。
4. `EnterWorktree` の結果に含まれるブランチ名を控える。`/test` フェーズでベースブランチへマージする際に必要になる(設計ドキュメントの「実装ステップ」欄などに一時的にメモしておいてよい)。

以降の実装・コミット・(委譲する場合は)`implementer` サブエージェントへの作業指示は、すべてこのワークツリー内で行う。他のセッションが並行して別トピックの `/implement` を実行していても、それぞれ別のワークツリー(別ディレクトリ・別ブランチ)で作業するため、ファイルの奪い合いは起きない。

## 手順

1. `docs/memory/MEMORY.md` を読む。特に convention(実装規約)・pitfall(既知の落とし穴)は関連するものを `docs/memory/entries/` で確認し、それに従って実装する。
2. 設計ドキュメントの実装ステップ(チェックリスト)に沿って、上から順に実装する。
3. 設計に書かれていない範囲まで勝手に拡張しない(スコープクリープの禁止)。設計との乖離が必要だと判明した場合は、作業を止めて理由を人間に報告し、設計ドキュメントを更新してから続行する。既存の共有メモリ(decision/convention)と矛盾する実装が必要だと分かった場合も同様に一度止めて報告する。
4. 意味のある単位でこまめに動作確認しながら進める(一気に全部書いてから最後にまとめて確認、を避ける)。
5. 実装が完了したら、設計ドキュメントの実装ステップのチェックリストにチェックを入れて更新する。
6. 実装中に他topicでも再発しうる落とし穴(pitfall)に遭遇した場合は `docs/memory/entries/` に追記し `docs/memory/MEMORY.md` を更新する。
7. **このワークツリー(トピック専用ブランチ)内でのコミットは、意味のある単位(実装ステップ完了ごとなど)で行ってよい。** ベースブランチとは分離されているため、こまめなコミットは安全かつ推奨される。ただし **ベースブランチへの `git merge` や `git push` は自分で行わない。** マージは `/test` でのゲート2承認後にのみ行う。

## 完了条件

- 設計ドキュメントの実装ステップがすべて完了している
- 実装内容がこのトピックのワークツリー内でコミットされている
- 次のアクションとして `/test` の実行を促すメッセージを出す

## 注意

このフェーズには人間確認ゲートはない。実装完了後は自動的に `/test` に進んでよい(同じワークツリー内で継続する)。ただし、設計からの逸脱・重大な技術的制約に直面した場合はその場で人間に報告してよい。
